# G2 Session Recovery Design

## Goal

Make HermesGlass resilient to G2, phone, network, bridge, and scan interruptions. A user who loses connection during an approval or scan should be able to reconnect and recover the current target, pending approvals, active grants, job status, recent output, and report links.

## Scope

This design covers all three recovery levels:

- reconnect soft state using a stable G2 client session id;
- durable SQLite state for approvals, grants, jobs, target/scope, and event replay;
- a bridge-owned job manager for long HexStrike scans that survives WebSocket disconnects.

This does not add new high-risk scan workflows. It defines how those workflows must behave once implemented.

## Core Principle

The WebSocket is a transport, not the owner of work. Disconnecting glasses must not cancel an approved scan or erase the state needed to explain what happened.

## Identity Model

The mobile app generates and persists:

- `clientSessionId`: unguessable random id, stable across reconnects for one EvenHub profile.
- `profileId`: stable id for the configured Hermes/bridge profile.
- `lastSeenEventId`: highest event id rendered or processed by the app.

The bridge treats `clientSessionId + profileId` as the G2 session key. A WebSocket connection attaches to that session, but the session can outlive any one connection.

Normal chat, action, approval, and job calls should use a session key derived from the same stable id, not the current socket lifetime.

## Protocol

### Resume

On connect, after bridge capabilities and target sync, the app sends:

```json
{
  "method": "g2.session.resume",
  "params": {
    "clientSessionId": "g2s_...",
    "profileId": "profile_...",
    "lastSeenEventId": 123
  }
}
```

The bridge responds:

```json
{
  "session": {
    "id": "g2s_...",
    "profileId": "profile_...",
    "target": "192.168.1.1",
    "scope": "authorized lab",
    "lastEventId": 130
  },
  "pendingApprovals": [],
  "activeGrants": [],
  "jobs": [
    {
      "id": "job_...",
      "workflow": "hexstrike-recon",
      "target": "192.168.1.1",
      "state": "running",
      "startedAt": 1782549000000,
      "reportUrl": "https://titagram.tail005130.ts.net:8899/g2-192-168-1-1/"
    }
  ],
  "missedEvents": []
}
```

If `lastSeenEventId` is too old and events have been compacted, the bridge returns a snapshot plus `missedEventsTruncated: true`.

### Event ids

Every `chat.event`, `agent.event`, `agent.completion`, `approval.created`, `approval.resolved`, and `job.updated` generated by G2 workflows gets a monotonic `eventId`.

The app records the last event id after rendering. On reconnect it asks for missed events and can rebuild the last visible state without relying on app memory.

## Storage

Use SQLite through Python stdlib `sqlite3`. Default path:

```text
~/.hermes-g2/state.sqlite3
```

Tables:

- `g2_sessions`: `client_session_id`, `profile_id`, target, scope, timestamps, active flag.
- `g2_events`: event id, session id, type, payload JSON, created timestamp.
- `g2_approvals`: approval id, session id, workflow, target, risk, status, options JSON, expiry.
- `g2_grants`: grant id, session id, workflow, target, risk ceiling, source channel, expiry.
- `g2_jobs`: job id, session id, workflow, target, state, pid, command JSON, report URL, log tail, timestamps, exit code.

Retention:

- completed events: keep last 500 per session or 24 hours, whichever is smaller;
- resolved approvals: keep 24 hours;
- expired grants: keep 24 hours for audit;
- completed jobs: keep 7 days of metadata, reports stay under HexStrike project retention.

## Job Manager

The bridge owns G2 jobs independently of the WebSocket connection.

For `hexstrike-recon`, approval creates or starts a durable job:

1. create `g2_jobs` row with `queued`;
2. start the bounded wrapper subprocess;
3. persist pid, command, target, report URL;
4. stream stdout to attached WebSockets and append compact output to job log tail;
5. update status to `succeeded` or `failed`;
6. emit `agent.completion` with the same status.

If no WebSocket is attached, the job continues. On reconnect, the app sees the job as active or completed and gets recent output plus report URL.

On bridge restart:

- jobs with live pids are reattached when possible;
- jobs without live pids are reconciled from wrapper output/report files;
- unknown jobs become `lost` with a clear status message and report link if one exists.

The job manager must not start duplicate jobs for the same session/workflow/target unless the user explicitly requests another run.

## Approval Recovery

Pending approvals are durable and have TTL.

Reconnect behavior:

- if an approval is pending and unexpired, it reappears as a high-priority surface item;
- if it expired, the bridge emits an expiration event and removes it from the active surface;
- `DETAIL` can be replayed after reconnect;
- `DENY` and approved states are idempotent.

Session grants are durable but bounded:

- same client session id;
- same profile id;
- same target;
- same workflow;
- risk not above ceiling;
- TTL valid.

Changing target or profile invalidates existing grants for action selection, even if rows remain for audit.

## High-Risk Grants

High-risk approvals must require mobile confirmation. The glasses may show `PHONE`, `DETAIL`, and `DENY`, but cannot create a high-risk grant.

The phone approval UI offers:

- `Approve once`;
- `Allow for this session`;
- `Deny`.

High session grants have short TTL, are tied to `clientSessionId + profileId + target + workflow`, and record `sourceChannel: "mobile"`. The bridge rejects `riskCeiling: high` if the response came from the glasses path.

## App Behavior

On startup:

1. load or generate `clientSessionId` for the active profile;
2. connect to bridge;
3. send `g2.target.set`;
4. send `g2.session.resume`;
5. render restored surface, active jobs, pending approvals, or latest chat output.

While connected:

- update `lastSeenEventId` after rendering events;
- display active job state on home, for example `RECON RUNNING`;
- opening an active job shows recent output and report URL;
- double press returns home, not cancel.

Cancellation should be an explicit future action with its own approval rules.

## Failure Cases

- Glasses disconnect during idle: reconnect restores target and surface.
- Glasses disconnect with pending approval: approval reappears until TTL expiry.
- Glasses disconnect with active grant: grant remains usable if TTL and binding match.
- Glasses disconnect during scan: scan continues, output is replayed on reconnect.
- Phone app killed during scan: bridge job continues; reconnect resumes by `clientSessionId`.
- Bridge restarts during scan: job manager reconciles pid/report and marks job active, succeeded, failed, or lost.
- Duplicate reconnects from same profile: newer connection attaches; older connection can still receive events until closed, but actions must be idempotent.
- Target typo or public CIDR: validation still runs before approval or job creation.

## Testing

- Unit tests for session id validation, event id ordering, grant recovery, expiry, and target/profile invalidation.
- Unit tests for job manager state transitions and duplicate job prevention.
- Integration tests for reconnect with pending approval, active grant, running job, completed job, and compacted event log.
- Remote probe against `wss://titagram.tail005130.ts.net:8448/ws` simulating disconnect during `hexstrike-recon`.
- Manual hardware test: start scan, force-close EvenHub or disable Bluetooth/network, reconnect, confirm current job and report URL recover.
